# Park/e63: 한 스텝 결정 계산 시간 (Kaggle DARROW)

상태: **완료 (2026-11-23). H1 기각 (차단 위 예측 제어 / 대표 = 2.2배).** 측정 방법과 가설은 측정 전에 정했다 (사전 등록 커밋 `669d66e`). 대표는 바꾸지 않는다.

## 목적

Park/e58 은 같은 차단 위에서 1시간 예측 제어가 학습 정책만큼 한다는 것을 보였다. 성능이 비슷하면 실제 적용에서는 계산 비용과 구현 부담이 고르는 기준이 된다. 학습 정책은 신경망 4개를 한 번씩 계산하고, 예측 제어는 매 스텝 후보 133개를 대리 모델 4개로 4 스텝씩 굴린다. 이 실험은 그 차이를 잰다. 팀 중간점검 (Yoo/analysis/TEAM_RESEARCH_REVIEW_20261117.md) 이 요구한 현장 적용 관점의 근거다.

## 방법

- 현장 한 곳 (에피소드 1개) 을 가정한다. 검증 40일에서 8일 간격 5일 x 구성원 0 을 돌며, 스텝마다 관측을 받아 차단까지 거친 행동을 내는 데 걸린 벽시계 시간을 잰다 (`time.perf_counter`). 환경 계산은 재지 않는다
- 방법: 대표 (묶음 0_1_2_3 + 대표 차단), 차단 위 예측 제어 (Park/e60 고름), 예측 제어만 (같은 설정, 차단 없음), 다시 고른 ABAC (Park/e54)
- 같은 측정을 3번 하고 스텝 시간 (5일 x 95 스텝 x 3번 = 1,425 개) 을 모아 중앙값, 평균, 95% 분위를 낸다. OMP 스레드 2, 다른 실험이 끝난 뒤 돈다
- 기계 정보 (`platform`) 를 함께 적는다

## 가설 (사전 등록)

- H1. 대표의 스텝 시간 중앙값이 차단 위 예측 제어의 1/10 이하다

## RESULT.md 처리 (미리 정함)

- H1 지지: "대표는 차단 위 예측 제어보다 한 스텝 결정이 10배 이상 빠르다" 고 적는다. 두 방법 모두 15분 스텝보다 훨씬 짧으면 그 사실도 적는다 (계산 시간이 실제 제약은 아님)
- H1 기각: "계산 시간 차이는 10배보다 작다" 고 적는다

## 미리 밝히는 한계

- 한 기계에서 잰 값이고 다른 프로그램의 부하에 따라 달라진다
- 예측 제어는 후보를 한꺼번에 계산하도록 벡터화되어 있지만 더 빠르게 구현할 여지가 있다. 학습 정책의 학습 시간은 재지 않는다 (한 번만 드는 비용)

## 결과

전체 표는 [results.md](results.md). 기계: macOS-26.7.1-arm64 (Apple 실리콘), OMP 스레드 2.

| 방법 | 스텝 시간 중앙값 ms | 평균 ms | 95% 분위 ms |
| --- | --- | --- | --- |
| 대표 (FCSRL 4 x 16 + 대표 차단, 묶음 0_1_2_3) | 96.82 | 103.72 | 180.86 |
| 차단 위 예측 제어 (Park/e60 고름) | 212.94 | 218.56 | 241.85 |
| 예측 제어만 (차단 없음) | 122.32 | 122.67 | 126.75 |
| 다시 고른 ABAC (Park/e54) | 0.01 | 0.01 | 0.01 |

- H1: 차단 위 예측 제어 / 대표 = 2.2배로 10배에 못 미친다. **기각**
- 참고: 두 방법 모두 스텝 간격 15분 (900,000 ms) 보다 3,700배 이상 짧다

## 해석

- 사전 등록 처리에 따라 "계산 시간 차이는 10배보다 작다" 고 적는다. 두 방법 모두 15분 스텝보다 훨씬 짧아 계산 시간은 실제 제약이 아니다
- 대표의 시간도 대부분 차단이 쓴다. 차단 위 예측 제어 (213) 와 예측 제어만 (122) 의 차이 약 90 ms 가 차단 몫이고, 대표 (97) 의 대부분이 같은 차단이다. 학습 정책 계산은 몇 ms 수준이다
- 따라서 계산 비용은 학습 정책을 고를 이유가 되지 않는다. 학습 정책은 대신 학습 시간 (한 번) 이 들고, 예측 제어는 학습이 필요 없다
